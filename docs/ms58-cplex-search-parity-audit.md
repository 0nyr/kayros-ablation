# ms58 CPLEX and search-control source audit

We compared corrected Kayros `327e481713e1b9a3187fda2fc9f10f8d9d75b0c5` with the minimally repaired Lera control `f2c9e205bd1ecc9afb45d5efe7fcb0df881f2b33`. This investigation changes no Kayros source and runs no solver or benchmark. It finds no CPLEX option mismatch in the selected paths, but confirms a shared algorithm-epsilon difference and several search-work and wrapper-overhead hypotheses. The separate EPS diagnostic source described below is unbuilt and unmeasured.

## EPS scope and isolated diagnostic derivative

The constants occur at line 17 of [Lera's number utilities](../../lera-proof-minimal-reference/code/goc/include/goc/math/number_utils.h) and [Kayros's number utilities](../../kayros-proof-best/cpp/lera/goc/include/goc/math/number_utils.h). This is a broad arithmetic convention, with the following uses:

- `Valuation::SetValue` removes values close to 0, and `Valuation::IsInteger` tests closeness to an integer. See [valuation.cpp](../../kayros-proof-best/cpp/lera/goc/src/linear_programming/model/valuation.cpp), lines 18 and 34.
- `BCP::Run` and `ProcessNode` compare lower and upper bounds. `BranchNode` filters fractional arcs, and `SeparateCuts` selects and admits violated cuts through the same predicates. See [bcp.cpp](../../kayros-proof-best/cpp/lera/main/src/bcp/bcp.cpp), lines 128, 272, 303, 428 and 438.
- `SPF::InterpretDuals` omits cut duals considered zero. See [spf.cpp](../../kayros-proof-best/cpp/lera/main/src/bcp/spf.cpp), line 99.
- Labeling uses epsilon predicates for negative reduced costs, dominance, merge rejection, capacity and time-window comparisons. See [bidirectional_labeling.cpp](../../kayros-proof-best/cpp/lera/main/src/labeling/bidirectional_labeling.cpp), lines 343, 428 and 565, and [monodirectional_labeling.cpp](../../kayros-proof-best/cpp/lera/main/src/labeling/monodirectional_labeling.cpp), lines 420, 433 and 532.
- PieceWise Linear geometry uses the same predicates for interval containment, empty or point domains, nearly equal slopes and endpoint coincidence. See [interval.cpp](../../kayros-proof-best/cpp/lera/goc/src/math/interval.cpp) and [linear_function.cpp](../../kayros-proof-best/cpp/lera/goc/src/math/linear_function.cpp).

A tighter EPS can change pricing work near termination, but it also changes intermediate geometry and dominance. Consequently its effect need not be monotone, and it cannot be interpreted as a change to the final stopping threshold alone. Matching EPS also leaves Kayros's arithmetic repairs, checked master coefficients and canonical reductions different from Lera.

At the managing agent's request, we prepared development branch `proof-speed/eps-parity` in `lera-proof-eps-parity`, commit `fe8e927cf5a7ade98ce0d698b4af402a0caa5652`, directly from the fixed Lera control. The [patch](../patches/ms58-experimental/lera-eps-parity.patch) changes exactly 1 line, `const double EPS = 10e-6;` to `const double EPS = 10e-7;`, preserving the file's original final-newline state. It changes no CPLEX tolerance, algorithm flag or Kayros file. The worktree is clean, and no build or solver execution was performed.

The fixed `f2c9e20` control remains mandatory. Any later test must identify the EPS derivative separately and rebuild all translation units that include the modified header. A useful diagnostic would retain fixed Lera, EPS-tightened Lera and corrected Kayros on the same Dabia n=100 tasks, first checking captured pricing work and near-threshold decisions, then interpreting paired solver outcomes. Checker-valid returned routes alone would not establish complete pricing. No speed claim or baseline substitution follows from this source change.

## CPLEX settings capture and cache conditions

Kayros's `record_ablation_settings` reads 7 integer parameters, 4 double parameters and the version, constructs JSON, and replaces the phase record on every LP or MIP solve. Lera's `ms56_observe` reads and emits settings only for the first call of each solve kind. The Kayros recorder sits inside the native LP/MIP stopwatch. Its `calls` field therefore counts a concrete repeated cost, including strong-branching LP probes that are not column-generation iterations.

This is a plausible small implementation overhead, not an established explanation of the large C104 gap. The [earlier instrumentation study](instrumentation-overhead.md) measured the combined supplemental instrumentation at +1 ms median native time on each of CPLEX C101 and R101. It did not isolate option capture or estimate C104 overhead. Current C104-specific capture cost remains unmeasured.

The recorded options are stable under a fixed configuration in the selected BPC path, but the generic solver API accepts mutable `config` JSON and uses different post-configuration reductions for LP and MIP separation. A safe cache proposal must retain call counters and read back on the first call or any change of CPLEX environment, configuration value, solve kind or separation-dependent override. It must reset when the bridge resets `ablation_backend_settings` at the start of each solve. Caching only by the string `lp` or `mip` would be insufficient for the generic interface. The time limit changes per call but is not among the captured fields. Parameter-setting calls and numerical values must remain unchanged. This proposal is unimplemented and needs measured work equality before any execution-speed interpretation.

## Shared master-wrapper costs and completeness obligations

Both LP wrappers snapshot every variable's domain, change the problem type to LP, optimize, then restore every domain individually. Each `GetVariableDomain` issues a single-column `CPXgetctype` and constructs a 3-entry `std::map`. Each `SetVariableDomain` constructs another map and issues a single-column `CPXchgctype`. The wrapper performs these operations for every column on every LP solve, including the up to 20 LP estimates for 10 strong-branching candidates. The type-save and type-restore loops lie outside the native LP stopwatch, while enclosing root or branching timers include them. They can therefore appear as search overhead rather than reported LP optimization time.

This implementation is shared by both engines. It becomes a discrepancy amplifier when their pool sizes or branch counts differ. A separately validated batching proposal could read all column types and restore them in bulk while preserving the exact final model and numerical settings. Actual basis reuse and degenerate-solution effects would still need checking. Likewise, the shared `SPF::SetForbiddenArcs` restores every route touched by the previous forbidden-arc set, then disables every route touched by the new set, potentially repeating bound changes for the same route. Deduplicating or batching these identical final bound assignments is a concrete source-level optimization candidate. Neither proposal is implemented or measured here.

The initial restricted master in both engines contains singleton routes. Kayros checks their costs and retains the legacy infinite-cost fallback for infeasible singletons, as documented in [lera_bridge.cpp](../../kayros-proof-best/cpp/lera/bridge/lera_bridge.cpp), lines 109–134. We found no separate phase-I or Farkas-pricing recovery in the selected BPC paths. Both `EstimateBound` methods map a restricted-master infeasibility to an infinite branch estimate, and both `ProcessNode` methods close a node when column generation returns restricted-master infeasibility. Restricted-master infeasibility alone does not establish infeasibility of the full column space. This is a shared completeness obligation already reflected in the unverified closure census, not a new observed counterexample or a performance optimization to exploit.

Kayros's admission ladder is also deliberately different. It escalates until a level adds new columns, and it requires a finished Exact pass on true duals before recording pricing exhaustion. Lera escalates while the returned route pool is empty and adds it directly. Both use the 3,000-route pool limit and the same heuristic-cost, heuristic-elementarity and Exact sequence in this protocol. Kayros's default stabilization parameter is 0, so enabled smoothing is not the explanation for this CPLEX comparison. The remaining differences involve correctness-preserving admission and arithmetic, rather than a discovered CPLEX configuration omission.
