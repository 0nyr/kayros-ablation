## Exact source semantics

In pinned Kayros `50eebc57964ac4f6762719ff21033783a31c12da`, `cpp/lera/bridge/lera_bridge.cpp` calls `checker_eval` before `spf.AddRoute`. The evaluator maps the native depot convention to customer IDs and calls `evaluate_route` on the untouched checker-convention instance. `cpp/core/route_eval.cpp` returns `feasible=false` when composing the route's temporal ready-time function leaves an empty feasible departure domain. This counter is therefore a disagreement between the labeling's proposed path and the internal temporal route evaluator. It is not a capacity-check counter and it does not, by itself, quantify the temporal violation or prove that the disagreement is harmless rounding.

The admission code skips the rejected route, increments `checker_infeasible_count`, and writes the warning. The rejected column does not enter the master LP. Its path fingerprint remains in the deduplication set. The source comment deliberately describes the nonzero counter as poisoning stricter certificate admission, because silently dropping columns could make pricing completion unsafe. The bridge still returns its native status and the count. The Python `optimality_metadata()` helper checks native `Optimum` status but does not itself enforce the rejected-column gate, so the caller or analyzer must preserve that distinction.

The completed Exact/CG census establishes participation and completion under the instrumented native control flow. It does not resolve the reason for the rejection. In the default non-step labeling pool, `BidirectionalLabeling::AddSolution` retains a best candidate per visited-customer set. It is consequently possible in principle for a rejected candidate to have displaced a feasible alternative that would still improve the master. No preserved artifact here demonstrates such an alternative or a material resulting bound error. This is a completeness hypothesis requiring evidence, not an observed counterexample or an additional formal-proof obligation imposed on the experiment.
