# Recorded resource outcomes

Resource exhaustion is an observed outcome under the declared per-process budget. It remains in every denominator, retains all independently checked incumbent points, and receives the full horizon when no closure is reported. A different memory-budget wave is a separate experiment. Raw harness statuses and return codes remain unchanged. Resource classification never excuses invalid candidates, integrity events, validation errors or result issues.

`analysis/pilot_summary.py::resource_failure_kind` recognizes 3 explicit contracts. A failed Python worker with exit 1 and a terminal `MemoryError` exception line is a recorded allocation failure. This records the exception without asserting whether the cause was an address-space cap, physical memory, fragmentation or another allocator constraint. A generic signal, nonzero exit or earlier mention of memory is insufficient.

For the frozen upstream executable, `code/src/main_bp.cpp:172–175` catches `std::bad_alloc` and returns 3 without printing a diagnostic or emitting `native_final`. The frozen `upstream_event_worker.py` explicitly propagates `process.wait()` through `raise SystemExit(code)` before publishing a sidecar. Classification therefore requires failed status, wrapper exit 3, arm `lera-exact`, the recorded command's actual adapter SHA256 `d16cffc4e1a82c7eb7ccea6d5ff90a1a67ec7fcc4817ce40d393678451b4eade`, and the binary selected by `manifest.worker_environment.UPSTREAM_PROBE_BINARY` having recorded SHA256 `fb05b79a48c2c338b4bec4efa72daf5e401c60a1c942b97d988ef95e3b56955b`. The run and manifest hashes must bind that identity to the result. Unknown executable or adapter versions and generic exit 3 remain unclassified failures. These are manifest attestations from the launch inventory, not a fresh execution of the binary during analysis.

Kayros's native RSS guard is distinct from allocator exceptions caused before that watermark. `cpp/lera/goc/include/goc/base/memory_monitor.h:45–55` polls RSS and makes `Exceeded()` sticky when RSS reaches the configured limit. `cpp/lera/bridge/lera_bridge.cpp:381–382` marks column generation `MemoryLimitReached`, and `cpp/lera/main/src/bcp/bcp.cpp:239–241` propagates that status to branch-and-cut. A normal wrapper exit can consequently carry `phase=exact_return, status=MemoryLimitReached` (or `exact_terminated`), while the native sidecar records `exact.exact_log.status` and `exact.memory.{limit_mb,peak_rss_mb,limit_reached}`. Analysis recognizes the recorded event only for hash-bound Kayros identities naming an exact-capable arm (`kayros-bpca-cplex`, `kayros-bpca-highs` or `kayros-full-cplex`), containing one of the frozen phase2 CPLEX or HiGHS `_lera` binary hashes and binding `identity.parameters.worker_sha256` to the audited adapter SHA256 `ccbf6eba1af213ceaba4cfc55d07bdab619e72474bd7ad2e266f6ccea031b029`. Kayros inventories pin installed modules in `runtime_files` and pin the actual worker separately in the run parameters. Event-file digests are checked before classification. This is a resource outcome even if the raw wrapper status is `completed`. It contributes no accepted proof or reported closure credit, and its checked incumbent trajectory remains usable. Any co-occurring raw closure event or accepted-proof claim is preserved explicitly and raises a review flag that blocks automatic recommendation, since these claims contradict the resource termination contract.

The original 8 GiB, 324-cell archive has 2 terminal Python allocation exceptions. Its 4 successful wrapper exits without closure are all native HiGHS `TimeLimitReached`: R201 repetition 3, R112 repetitions 2 and 3, and C201 repetition 1. None is a graceful native memory-limit return. No observations or scores are changed by this source-contract extension.
